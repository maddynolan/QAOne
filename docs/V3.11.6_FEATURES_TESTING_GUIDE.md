## 1. Cross-Browser Recording

### What It Does
Record browser interactions in **Chromium** (default), **Firefox**, or **WebKit (Safari)** — all from the same toolbar dropdown. Previously, recording was Chromium-only.

### How to Test

**Step 1: Open the Recorder**
- Navigate to **Record & Playback** in the sidebar
- You should see the recording controls panel at the top

**Step 2: Select a Browser Engine**
- Look for the **Globe icon dropdown** in the recording toolbar (after the network/device selector)
- Click it to see three options:
  - **Chromium** (default)
  - **Firefox**
  - **WebKit (Safari)**

**Step 3: Record in Firefox**
1. Select **Firefox** from the browser dropdown
2. Enter a URL (e.g., `https://example.com`)
3. Click **Start Recording**
4. Verify that a **Firefox** browser window opens (not Chrome)
5. Perform a few clicks and navigations
6. Click **Stop Recording**
7. Verify that recorded steps appear in the step list

**Step 4: Record in WebKit**
1. Select **WebKit (Safari)** from the browser dropdown
2. Enter a URL
3. Click **Start Recording**
4. Verify that a **WebKit** browser window opens
5. Record some interactions and stop

**Step 5: Verify Cross-Browser Playback**
1. Record a test in one browser (e.g., Chromium)
2. Switch browser to Firefox
3. Play back the recorded test
4. Verify steps execute correctly in the different engine

### Expected Behavior
- Browser dropdown shows all three engines with a Globe icon
- Each engine launches the correct browser (visually different window chrome)
- Recorded steps are engine-agnostic (work across browsers)
- If Firefox/WebKit is not installed, Playwright auto-downloads it on first use

### Troubleshooting
- If browser fails to launch, run `npx playwright install firefox webkit` in the project root
- Channel fallback (chrome, msedge) only applies to Chromium engine

### Files Involved
| File | Role |
|------|------|
| `src/modules/recorder/pages/PlaywrightRecorderPage.tsx` | `selectedBrowser` state, passed as `browserType` |
| `src/modules/recorder/components/RecordingControlsPanel.tsx` | Browser `<Select>` dropdown UI |
| `flowstral-desktop/src/main/playwright-recorder.js` | `launchBrowserWithFallback()` — selects engine |
| `flowstral-desktop/src/main/index.js` | IPC handler passes `browserType` to recorder |

## 2. Mobile Device Lab — Real Device IPC

### What It Does
The Device Lab tab now performs **real device operations** instead of showing fake/stub data:
- **Take Screenshot** — captures a real screenshot from the connected device
- **Stream Logs** — real-time logcat (Android) or syslog (iOS) streaming
- **Install App** — installs APK/IPA files onto the device
- **Uninstall App** — removes an app by bundle ID
- **Browse for App** — native file picker for APK/IPA selection

### How to Test

#### A. Real Screenshots

**Step 1: Connect a Device**
1. Start an Android emulator or connect a physical device via USB
2. Open **Mobile Testing** > **Device Lab** tab
3. Select your platform (Android/iOS) and device from the dropdowns

**Step 2: Take Screenshot**
1. Open any app on the device/emulator
2. Click the **Screenshot** button (Camera icon)
3. Wait 2-3 seconds for the capture

**Expected:** A real screenshot of the device screen appears in the preview area (base64 image rendered inline). Previously this showed a placeholder toast.

#### B. Live Log Streaming

**Step 1: Start Log Capture**
1. In Device Lab, click **Start Capture** (or the Play icon in the Logs section)
2. Optionally enter a filter string (e.g., `MyApp` or `Error`)

**Step 2: Generate Activity**
1. Open/use apps on the connected device to generate log entries
2. Watch the log panel update in real-time

**Step 3: Stop Capture**
1. Click **Stop Capture** to end the stream
2. Logs remain visible for review

**Expected:** Real logcat/syslog lines stream into the UI. Lines update every few hundred milliseconds. Filter narrows results.

**How it works internally:**
- Android: `adb logcat` spawned as child process, stdout piped to `mobile-log-line` IPC events
- iOS: `xcrun simctl spawn log stream` spawned similarly

#### C. App Install / Uninstall

**Step 1: Browse for APK/IPA**
1. Click the **Browse** button next to the app path input
2. A native file dialog opens filtered to `.apk` and `.ipa` files
3. Select your app file

**Step 2: Install**
1. Click **Install App**
2. Wait for the installation to complete (progress shown via toast)

**Expected:** The app appears on the device. Toast shows success or error message.

**Step 3: Uninstall**
1. Enter the bundle ID (e.g., `com.example.myapp`) in the bundle ID field
2. Click **Uninstall**

**Expected:** The app is removed from the device.

### Files Involved
| File | Role |
|------|------|
| `src/modules/mobile-testing/components/MobileDeviceLab.tsx` | UI — calls `mobile.takeScreenshot()`, `mobile.startLogs()`, etc. |
| `src/lib/electron-bridge.ts` | `mobile` export with IPC wrappers |
| `flowstral-desktop/src/main/webapp-preload.js` | Preload bridge exposing mobile methods |

## 3. Mobile Inspector — Real Element Hierarchy

### What It Does
The Inspector tab now fetches the **real UI element tree** from the connected device instead of displaying hardcoded sample data.

### How to Test

**Step 1: Connect Device**
1. Start an Android emulator with an app open
2. Go to **Mobile Testing** > **Inspector** tab

**Step 2: Fetch Hierarchy**
1. Click the **Refresh** button
2. Wait 3-5 seconds (uiautomator dump can be slow)

**Expected:**
- A tree view appears showing the real UI element hierarchy
- Each node shows: class name, resource-id, text, bounds, content-desc
- Expanding nodes reveals child elements
- Clicking a node highlights its properties

**Step 3: Verify Properties**
1. Click on any element in the tree
2. Check the properties panel on the right
3. Verify that `resource-id`, `text`, `bounds`, `class` match what's on screen

### Graceful Degradation
- If no device is connected or the command fails, the Inspector falls back to the built-in `SAMPLE_TREE` data
- A toast notification indicates whether real or sample data is being displayed

### How It Works
- Android: `adb shell uiautomator dump /dev/tty` returns XML → parsed with `DOMParser` via `parseXmlHierarchy()`
- iOS: `xcrun simctl ui describe-all` returns text (less structured)

### Files Involved
| File | Role |

| `src/lib/electron-bridge.ts` | `mobile.getHierarchy()` |
| `flowstral-desktop/src/main/lib/maestro-integration.js` | `MaestroRunner.getElementHierarchy()` |

## 4. Mobile Advanced Tools

### What It Does
Six advanced testing tools are now **wired to real device commands** via IPC. Previously all were stubs showing fake success toasts.

### 4A. Deep Links

**How to Test:**
1. Go to **Mobile Testing** > **Tools** tab
2. In the **Deep Links** section, enter a URL scheme (e.g., `myapp://profile/123` or `https://example.com/page`)
3. Click **Open Deep Link**

**Expected:** The device opens the URL — either in the target app (for custom schemes) or in the browser (for http/https).

**Verify:** Check the device screen to confirm the correct screen/page opened.

**How it works:**
- Android: `adb shell am start -a android.intent.action.VIEW -d <url>`
- iOS: `xcrun simctl openurl booted <url>`

### 4B. Push Notifications

**How to Test:**
1. In the **Push Notifications** section, configure:
   - **Title**: e.g., `Test Alert`
   - **Body**: e.g., `This is a test push notification`
   - **Bundle ID**: The app's bundle identifier (uses store value if set)
2. Click **Send Notification**

**Expected:** A push notification appears on the device.

**How it works:**
- Android: `adb shell am broadcast` with intent extras for title/body
- iOS: `xcrun simctl push booted <bundleId> <temp-json-file>` (creates a temporary APNs payload file)

### 4C. Biometric Simulation

**How to Test:**
1. Open an app that uses fingerprint/face authentication on the device
2. Trigger the biometric prompt in the app
3. In the **Biometrics** section, click **Simulate Success** or **Simulate Failure**

**Expected:**
- **Success**: The app proceeds as if the fingerprint/face was matched
- **Failure**: The app shows an authentication failure

**How it works:**
- Android: `adb shell am broadcast -a com.android.internal.FINGERPRINT_AUTH` with success/failure extras
- iOS: `xcrun simctl spawn notifyutil -s com.apple.BiometricKit.enrollmentChanged` + matching/failure notification

### 4D. Geolocation

**How to Test:**
1. In the **Geolocation** section, enter coordinates:
   - **Latitude**: e.g., `37.7749` (San Francisco)
   - **Longitude**: e.g., `-122.4194`
2. Click **Set Location** (or select a saved location and click it)

**Expected:** The device's GPS location changes. Verify by opening a maps app on the device.

**Saved Locations:** Pre-configured locations (stored in Zustand) can be clicked to quickly set common test locations.

**How it works:**
- Android: `adb emu geo fix <lng> <lat>` (note: longitude first for adb)
- iOS: `xcrun simctl location booted set <lat> <lng>`

### 4E. Network Conditioning

**How to Test:**
1. In the **Network Conditioning** section, select a profile:
   - **3G Slow** / **3G Fast** / **LTE** / **WiFi** / **Offline** / custom profiles
2. Click the profile to apply it

**Expected:** Network speed on the device changes. Test by loading a web page — it should load slower on 3G profiles.

**Reset Network:**
1. Click the **Reset** button to restore full connectivity

**How it works:**
- Android: `adb shell svc wifi enable/disable` + `adb shell svc data enable/disable`
- iOS: Requires Network Link Conditioner (note displayed in UI)

### 4F. Device Configuration

**How to Test:**

**Orientation:**
1. In the **Device Config** section, click **Portrait** or **Landscape**
2. **Expected:** Device rotation changes

**Appearance (Dark/Light Mode):**
1. Click **Light** or **Dark**
2. **Expected:** Device switches between light and dark mode themes

**Locale:**
1. Select a locale from the dropdown (e.g., `fr-FR`, `ja-JP`, `es-ES`)
2. Click **Apply**
3. **Expected:** Device language/region changes (may require app restart)

**Font Scale (Accessibility):**
1. Click one of the scale buttons: **Small (0.85x)**, **Default (1.0x)**, **Large (1.3x)**, **Extra Large (1.5x)**
2. **Expected:** Text size across the device changes

**How it works:**
- Orientation: `adb shell settings put system user_rotation`
- Appearance: `adb shell cmd uimode night yes/no` (Android) / `xcrun simctl ui appearance` (iOS)
- Locale: `adb shell setprop persist.sys.locale` (Android) / `xcrun simctl spawn defaults write` (iOS)
- Font Scale: `adb shell settings put system font_scale` (Android) / `xcrun simctl spawn defaults write` (iOS)

## 7. Performance — Server-Side Execution

### What It Does
Breaks the 20 virtual user (VU) ceiling by offloading load test execution to the backend `PerformanceEngine`. The in-browser mode runs VUs as concurrent `fetch()` calls in the browser (limited to ~20 before the browser tab crashes). Server-side mode uses the backend, supporting up to **10,000 VUs**.

### How to Test

**Step 1: Enable Server Runner**
1. Go to **Performance** testing page
2. Look for the **"Run on Server"** toggle switch near the VU configuration
3. Enable it

**Step 2: Configure High VU Count**
1. Set virtual users to a number above 20 (e.g., **100 VUs**)
2. Note: With server mode off, the slider caps at 20. With server mode on, it allows up to 10,000

**Step 3: Configure Test**
1. Enter a target URL
2. Set duration, ramp-up, and load pattern as needed

**Step 4: Run the Test**
1. Click **Run Load Test**
2. Watch the progress indicators — the test runs on the backend, not in-browser

**Expected behavior during server-side execution:**
- `POST /api/performance/scenarios` creates a scenario on the backend
- `POST /api/performance/scenarios/{id}/steps` adds the HTTP request steps
- `POST /api/performance/tests/run` starts the load test
- The UI polls `GET /api/performance/tests/{id}/status` every 2 seconds
- Progress is displayed in the UI (status, current VUs, requests completed)
- On completion, results (response times, throughput, error rates) are added to test history

**Step 5: Verify Results**
1. After the test completes, check the results panel
2. Metrics should show realistic server-generated data (not browser-simulated)
3. Response time percentiles, throughput, and error rates should be present

### Backend Requirements
The backend must be running with the performance engine available:
- `POST /api/performance/scenarios` — must return `{ id: "..." }`
- `POST /api/performance/tests/run` — must accept scenario ID and return test ID
- `GET /api/performance/tests/{id}/status` — must return status updates

### Files Involved
| File | Role |
|------|------|
| `src/modules/performance/pages/Performance.tsx` | `useServerRunner` toggle, server-side execution flow, polling logic |
| Backend `performance_api.py` | Scenario creation, test execution, status polling endpoints |

## 8. Performance — HAR Import

### What It Does
Import HTTP Archive (HAR) files to automatically configure load test scenarios. The HAR file contains recorded HTTP requests which are extracted and used as test steps.

### How to Test

**Step 1: Get a HAR File**
1. Open Chrome DevTools > Network tab
2. Perform some actions on a website
3. Right-click in the Network tab > "Save all as HAR with content"
4. Save the `.har` file

**Step 2: Import HAR**
1. Go to **Performance** testing page
2. Switch to the **Custom Config** tab
3. Find the **HAR Import** card
4. Click the file input and select your `.har` file

**Expected:**
- The file is uploaded via `POST /api/import/har` (FormData)
- Requests are extracted from the HAR file
- The base URL is auto-detected from the first request entry
- URL field is populated with the detected base URL
- A success toast shows how many requests were imported

### Files Involved
| File | Role |
|------|------|
| `src/modules/performance/pages/Performance.tsx` | HAR import card UI, file upload handler |
| Backend `api_import_api.py` | `POST /api/import/har` endpoint |

## 9. Performance — Test History Persistence

### What It Does
Performance test results now **survive page refreshes**. Previously, navigating away from the Performance page lost all test history.

### How to Test

**Step 1: Run a Test**
1. Execute any load test (browser or server mode)
2. Verify results appear in the test history panel

**Step 2: Refresh the Page**
1. Press F5 or navigate away and back
2. Check the test history panel

**Expected:** Previous test results are still visible. History is stored in `localStorage` under key `flowstral-perf-history` (max 50 entries).

**Step 3: Verify Limit**
1. Run many tests (or inspect localStorage directly)
2. Confirm that only the most recent 50 entries are kept

### Files Involved
| File | Role |
|------|------|
| `src/modules/performance/pages/Performance.tsx` | `useState` lazy initializer loads from localStorage; `useEffect` saves on changes |

### IPC Architecture (4-Layer Stack)

```
React Component (e.g., MobileAdvancedTools.tsx)
    ↓ calls
electron-bridge.ts → mobile.openDeepLink(platform, deviceId, url)
    ↓ invokes
webapp-preload.js → ipcRenderer.invoke('mobile-open-deep-link', {...})
    ↓ handled by
index.js → ipcMain.handle('mobile-open-deep-link', ...)
    ↓ calls
maestro-integration.js → MaestroRunner.openDeepLink(url, deviceId)
    ↓ executes
adb shell am start -a android.intent.action.VIEW -d <url>
```

### Common Troubleshooting

| Issue | Solution |
|-------|----------|
| Mobile features show "Not available in browser" | Must run in Electron desktop app, not web browser |
| "No device connected" | Run `adb devices` (Android) or check Simulator.app (iOS) |
| Screenshot fails | Ensure only one device/emulator is running, or specify device ID |
| Logs don't stream | Check adb connection; try `adb logcat` manually |
| Firefox/WebKit not launching | Run `npx playwright install firefox webkit` |
| Server test polling never completes | Verify backend is running at the configured API URL |
| HAR import fails | Ensure the HAR file is valid JSON (Chrome DevTools format) |
| Test history lost | Check localStorage — `flowstral-perf-history` key; clear browser cache may remove it |
| Biometric simulation no effect | App must be actively showing biometric prompt |
| Deep link opens browser instead of app | App must have the URL scheme registered in its manifest |

### Regression Fixes in v3.11.6

| Fix | What Was Wrong |
|-----|----------------|
| `electronAPI.on` validChannels | `mobile-log-line` and `mobile-studio-output` were missing from the `electronAPI.on` whitelist (only in `flowstral.on`), causing silent event drops |
| Performance poll cleanup | `setInterval` for server test polling was not cleaned up on component unmount (memory leak) |
| Import ordering in MobileInspector | `parseXmlHierarchy()` was placed between import blocks (cosmetic) |
| Shell injection in uninstallApp | `bundleId` parameter was unquoted in `execSync` commands |
